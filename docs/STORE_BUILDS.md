# Store builds

How the App Store (and later Google Play) build of HisFullGlory is made. Written 2026-11-02 with plan 02-01 of
phase 2. Decisions D-01 to D-03 and D-14 are in the phase context; the route is summarised in
[APP_STORES.md](APP_STORES.md).

## What the store build is

- The same React app as app.hisfullglory.com, built with `npm run build:native` (`vite build --mode native`).
- **Bundled:** the app, the Bible (`bible/web.json`), study files, AI explanations and fonts are inside the app
  package. The app opens and reads offline. Content added to the website later (AI explanations, context
  checks) reaches store users only with the next store build.
- **No service worker and no web manifest.** `VitePWA` gets `disable: true` in native mode. The web build is
  unchanged and keeps both; `tests/native-*.test.ts`, `npm run check:native` and the browser checks prove each side.
- **No remote start address.** `capacitor.config.ts` has no `server` block. iOS serves the app from
  `capacitor://localhost`, Android from `https://localhost`. Never change these, the bundle ID
  `com.hisfullglory.app` or the scheme after the first release: the reader's journal, progress and session live
  in storage that belongs to that address.
- **Guards at build time** (`src/native/buildGuard.ts`): a store build stops if `VITE_SUPABASE_URL` has a path,
  a query, credentials or plain http (the 2026-10-08 `/rest/v1/` outage), or if `VITE_SUPABASE_ANON_KEY` is not a
  public key (publishable or anon). It also always applies the production rule for the legal text, whatever
  `VERCEL_ENV` says. Pull-request checks build without Supabase values; the hand-run workflow requires both
  (`scripts/store-env-check.mjs`).
- **Identity:** bundle ID `com.hisfullglory.app`, name HisFullGlory, version 1.0.0, iPhone and iPad in every
  orientation (D-14).

## The iOS project (`ios/`)

Generated with `npx cap add ios` (Capacitor 8.5.3, Swift Package Manager, iOS 15 and later) and then edited as
text on Windows:

- `ios/App/App/Info.plist`: display name, `ITSAppUsesNonExemptEncryption` = NO (only the encryption built into
  iOS, so no export questionnaire on each upload), orientations for iPhone and iPad.
- `ios/App/App/App.entitlements`: Sign in with Apple (`Default`), needed in the profile from the first build.
- `ios/App/App/PrivacyInfo.xcprivacy`: file timestamps, reason C617.1 (the Filesystem plugin); no tracking and no
  collected data declared by the app itself.
- `ios/App/App.xcodeproj/project.pbxproj`: the **App target only** signs Release manually with team
  `5ZYRJ5FZPU`, identity "Apple Distribution" and the profile named "HisFullGlory App Store". Debug keeps
  automatic signing. These settings are never passed on the `xcodebuild` command line, where they would also hit
  the Swift package targets.
- `ios/ExportOptions.plist`: App Store Connect export, manual signing, upload straight to App Store Connect.
- Icon and launch screen come from the unchanged logo (`public/icon.svg`): `node scripts/native-assets.mjs` writes
  `assets/`, then `npx @capacitor/assets generate --ios` writes the asset catalog. The icon has no alpha channel;
  the launch screen has a light (#F6F0E7) and a dark (#1A120E) version.
- The copied web build (`ios/App/App/public`), `capacitor.config.json` and `config.xml` are generated by
  `npx cap sync ios` and are not committed (`ios/.gitignore`).

## GitHub environment `store-release`

Set up by the founder (plan 03), never by Claude. Settings > Environments > New environment `store-release`,
deployment branches limited to `main` and `store-shell`. Only workflows that name this environment can read its
values, and only from those branches.

| Name | Kind | What it holds | Who sets it |
| --- | --- | --- | --- |
| `IOS_DIST_CERT_P12` | secret | base64 (one line) of the Apple Distribution certificate with its private key (`.p12`) | founder |
| `IOS_DIST_CERT_PASSWORD` | secret | the password of that `.p12` | founder |
| `IOS_PROFILE` | secret | base64 of the App Store profile "HisFullGlory App Store" (`.mobileprovision`) | founder |
| `ASC_KEY_P8` | secret | base64 of the App Store Connect API key file (`AuthKey_<id>.p8`), role App Manager | founder |
| `ASC_KEY_ID` | secret | the key's ID (kept as a secret so it never appears in logs) | founder |
| `ASC_ISSUER_ID` | secret | the issuer ID shown above the keys list | founder |
| `VITE_SUPABASE_URL` | variable | the bare project address, `https://<project>.supabase.co` | founder |
| `VITE_SUPABASE_ANON_KEY` | variable | the publishable (or anon) key, which is public by design | founder |

The team ID `5ZYRJ5FZPU` is public (it is in every signed app) and is committed in the project and in
`ExportOptions.plist`, so no `APPLE_TEAM_ID` variable is needed. Values are never written in this repository, in
an issue, in a pull request or in a chat; base64 is made with `base64 -w0 file > file.b64` in Git Bash.

## Running "iOS TestFlight"

1. GitHub > Actions > **iOS TestFlight** > **Run workflow** > choose the branch (`main` or `store-shell`) > Run.
2. The job (`.github/workflows/store-ios.yml`, macOS 26 runner, Xcode 26.6, at most 45 minutes) checks the two
   Supabase values, builds the store bundle, copies it into the iOS project, sets up signing in a temporary
   keychain, archives, exports and uploads. The last step always deletes the keychain and every decoded file.
3. After Apple has processed the build (often 5 to 30 minutes) it appears under TestFlight in App Store Connect.
   Internal testers (App Store Connect users, such as the founder) can install it without Beta App Review.

Safety rules, enforced by `tests/store-workflows.test.ts`: the workflow runs only by hand, never for a pull
request; it uses the `store-release` environment and read-only repository access; each secret appears only as a
step's env entry; commands are never traced; the failure note reads only the build, archive and export logs.
The pull-request checks (`checks.yml`) build the store bundle and run its browser check without any secret.

**Build numbers:** `CURRENT_PROJECT_VERSION` is the workflow's run number, so every run uploads a new build number
(a reused number is refused). The version shown in the store is `MARKETING_VERSION` (1.0.0) in the project.

## Proven and not yet proven

Proven on Windows (2026-11-02): the store bundle builds, has no service worker or web manifest, opens Today and
the Bible with nothing fetched from another host; the web build still has its service worker; `npx cap add ios`
and `npx cap sync ios` run; the project files say what is described above (tests read them as text).

**Not proven until the first workflow run** (plan 04): that the iOS project compiles under Xcode 26.6, that every
plugin resolves under Swift Package Manager, that the scheme `App` is found, that manual signing of the App target
works with the Swift package targets, that the `.p12` imports, and that `xcodebuild` uploads directly with the
API key. Nothing here may be called built, signed or working before that run and the founder's install.

## Fallbacks, in order (D-03)

1. **Upload with altool:** change `destination` in `ExportOptions.plist` to `export` and upload the `.ipa` with
   `xcrun altool --upload-app --type ios --apiKey <id> --apiIssuer <issuer>` (key file in
   `~/.appstoreconnect/private_keys/`), if the direct upload by `xcodebuild` fails.
2. **Cloud signing:** `-allowProvisioningUpdates` with an App Store Connect key of role Admin, if manual signing
   cannot be made to work. Costs: an Admin key in CI, and a new certificate on fresh runners.
3. **Codemagic** (free tier, 500 macOS minutes a month), if GitHub's macOS runners cannot do it. A third party then
   holds the API key.
