# Private data and account boundaries

| Data | Stored / sent | Visibility |
|---|---|---|
| Journals, notes, prayers/answers, struggles, preferences, reading/progress | Local v3 profile only | Guest or matching signed-in account UI; never automatically uploaded |
| Followed topics, saved discussion links, paths/challenge progress | Local profile | Private; following never implies server membership |
| Community membership | community_memberships via explicit join/leave RPC | Matching owner only; no public member directory |
| Public post/reply/source | Explicit public composer RPC | Constrained visible/unblocked readers; staff retain accountable author ownership |
| Votes | Server-owned community_votes | Counts/current user's own vote only; raw voter rows inaccessible to app roles |
| Reports, blocks, moderation notes | Existing private tables/RPCs | Existing owner/operator rules; not public |
| Testimony relationship | Returned public UUID stored on private prayer | Local only; private prayer ID/body never sent as a relationship |
| Theme hint | hfg-appearance | Nonsensitive shared-device appearance hint |
| Sign-in email address | Held by Supabase Auth (`auth.users`) when someone asks for a sign-in code. Supabase sends the mail through Resend once the custom SMTP sender is set up (plan 01-11); until then it uses Supabase's own sender. No table in `public` has an email column: `profiles` holds only `display_name`. | Never shown to other people; not in posts, reports or exports |
| Push subscriptions | `push_subscriptions` (010): the browser's push address (`endpoint`, only the four push services of the allow-list), its two keys (`p256dh`, `auth`), the optional account id, `daily`, `reminder_time`, `time_zone`, `prayed_for` and timestamps. `push_outbox` queues only the fixed kinds `prayed_for` and `test`. Saved only after the person turns reminders on, as a guest or signed in. | No client can read either table (all rights revoked); written through `save_push_subscription`. The texts are fixed in `supabase/functions/push-sender` and never contain what anyone wrote |
| Word filter | `blocked_terms` (008): a list of words, no personal data. Text containing one of them is refused before it is stored (posts, replies, chat messages, prayer requests, display names, Circle names and answers, support requests). | Operator only; a refused text is not kept |
| Reports and holds | `community_reports` (001, 013): reporter, target, one of the report categories, an optional note of at most 1000 characters, status. At two different reporters (neither the author) the item is hidden until a person has looked at it (migration 013, applied to the hosted project in plan 01-05; the hold does not exist there before that); `moderation_audit` records the decision with no name or text. | Reporter and operators only; the reported person is never told who reported. No report text goes into email, push, analytics or URLs |
| Copy of the latest post | `community_posting_limits.last_body` (001): the text of each account's most recent post, kept only to block an identical repeat post and to enforce a 30-second pause. | No client can read it; deleted with the account (foreign key cascade) |

Guest uses hfg-daily-walk:v1/v2/v3. Accounts use hfg-private:<account-id>:<key>. Auth readiness gates rendering; changing account remounts the provider and drafts. Stale Terms responses cannot authorize a later account; token refresh rechecks acceptance. Signing in never automatically merges/adopts guest state. Existing pre-expansion local records have no trustworthy account ownership and remain in the guest profile; signing out returns to that profile.

Local storage and exported backups are **unencrypted**, browser/device-specific and inspectable through developer tools or another same-origin script. This is account separation in the application, not a device lock or encrypted storage. Shared-browser tabs in the same profile are not synchronized or transactionally coordinated; concurrent edits can overwrite a later save. Do not clear browser storage without a private backup. No cross-device restore or encrypted sync is configured. Signed-in people can delete their account in the app (see "Account deletion" below); that removes what the server holds for it and what the account saved on that device.

Migration reads v1 through the retained v2 transformation, normalizes v2 into v3, and preserves source bytes. Current corrupt/unknown v3 blocks writes. Normalization preserves original data in recovery snapshots; full/unavailable storage does not claim a save. Explicit recovery after export first retains current v3, then uses the latest readable retained v2, otherwise available v1 (or fresh state). Recovery keys do not replace earlier snapshots. Backup enumeration is scoped; the guest export cannot enumerate account data.

Recommendations take only explicit topic IDs/following. They never inspect journal/prayer bodies, send preferences to analytics or join a community. Sensitive choices do not influence commerce or public reputation. Serious-topic guidance precedes encouragement; no unverified local emergency numbers are invented. Source links do not fetch previews, so no preview SSRF flow exists. No dynamic/private/API/payment response is precached.

Public sources are unverified user attachments, rendered as text. HTTPS DNS links reject credentials, ports, IP/private host literals, control characters and backslashes. Destination domains are visible; external tabs use noopener/noreferrer. A DNS hostname can still resolve privately or host misinformation; no server/client preview fetch follows it and moderators must evaluate source claims. Sharing always requires a separate explicit Publish action.


## Circle boundaries
Only public Circle metadata/discussions are available to guests. Signed-in users may discover a private Circle's name, description, topic, privacy and question; nonmembers receive no exact count, members, applicants or discussion content. Active current members can read private discussions; pending/declined/left/removed accounts cannot. Broad discovery/detail metadata never includes application answers, including the caller's own answer. read_own_circle_application reads only the caller's record. Current owner/moderators use read_circle_members for pending answers; ordinary active members cannot.

Answers (max 1000 characters, plain text) remain only while pending, to support a review decision. They are immediately erased on approval, decline, withdrawal, removal or closure. Pending applicants can withdraw at any time; there is no time-based automatic purge job or indefinite post-decision retention claim. Closing preserves membership/post records but makes the Circle unavailable; hard owner-account deletion cascades its Circle and posts, and applicant account deletion cascades membership. Deleting an account (migration 007, see "Account deletion" below) also closes the Circles it owns, with their posts, because no ownership succession exists in v1. How long copies survive in the hosting provider's backups after a deletion is not known from the code; it is for the founder to read from the dashboards and state (P9 in `site/src/data/legal.ts`).

Private answers and group content are held in transient React memory only, never localStorage, URLs, analytics, notifications, logs or shared PWA caches. Application RPCs must not be logged by external observability tooling. Copy links contain only immutable Circle slug and thread UUID; receiving a link never grants private access. Reports keep reporter UUID/details private to the reporter/platform operators; scoped Circle reviewers see only category, target contribution, state and display snapshot. Blocks/mutes hide normal discussion authors/children without preventing legitimate scoped application/report review.

## Account deletion (migration 007, `DeleteAccount` in `src/platform/auth.tsx`)
Signed-in people delete their account on the Profile page (type DELETE, confirm). `delete_my_account()` deletes the row in `auth.users` and every foreign key to it cascades (checked on the hosted project on 2026-10-14), so the server no longer holds: the profile and display name, legacy chat and prayer messages, community posts and the replies other people wrote under them, reactions and votes, the reports the person sent, blocks and mutes in both directions, terms acceptance, topic and Circle memberships (and any pending answer), the posting-limit row with its copy of the latest post, support requests, Circles the person owns with their posts, and push subscriptions linked to the account (010: `user_id references auth.users on delete cascade`). A guest's push subscription has no account and is removed only when the person turns reminders off.

Kept: the moderation record (`moderation_audit`: which item, old and new state, time; no name, email address or text) and reports other people sent about the person's posts, which stay with their accounts. Not known from the code: how long Supabase Auth's own logs and the hosting provider's backups keep copies. The policy must not say "everything is removed" for those; the founder states them (P9 in `site/src/data/legal.ts`).

On the device, the app removes every `hfg-private:<account-id>:` entry of that account (`forgetAccount`), sets the session key `hfg-account-deleted` for the confirmation and signs out locally. What a guest saved on the device (`hfg-daily-walk:v1|v2|v3`) and other accounts' entries stay. The public page `/delete-account` says the same; `tests/account-deletion-schema.test.mjs` covers the SQL.

## Storage names (what our code keeps in the browser)
Local storage: `hfg-theme` (website theme choice), `hfg-appearance` (app theme hint), `hfg-reminder` (the reminder form's last values), `hfg-daily-walk:v1`, `v2`, `v3` (guest profile), `hfg-private:<account-id>:<key>` (an account's private data on that device), and the sign-in session that Supabase's library keeps under its own key after sign-in. Session storage: `hfg-account-deleted` (removed again as soon as the deletion confirmation has been shown). Our code sets no cookies. Local data is unencrypted (see above).
