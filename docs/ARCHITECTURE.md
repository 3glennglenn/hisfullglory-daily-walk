# Architecture

## Application and modules

`src/main.tsx` loads `platformApp.tsx`. The shell provides Today, Bible, Pray, Community and You (a floating tab bar, or a sidebar from 768px); You links Days walked, My Walk, Journal, Grow, Your shelf, Settings (with Appearance), Give, the Shop card (opens `/shop`) and Account; Today has a shopping-bag button that opens `/shop` too. `platform/router.ts` parses stable URL paths and query tabs with native history/popstate; there is no routing dependency. Hosts must use the documented SPA fallback. Auth links return to the origin root.

`platform/store.tsx` owns local state and atomic browser writes. `platform/persistence.ts` migrates preserved v1→v2→v3 and v2→v3 state. `storage.ts` retains the original calendar/plan model and regression behavior. Original journals become typed journal entries; edits/deletion of migrated entries mirror the legacy journal map within the retained legacy submodel to avoid resurrection. The original v1 key is never overwritten or deleted. Unknown/corrupt current v3 blocks writes and offers export/recovery. Normalized original v2 data is retained under a recovery key. Storage failures show a notice instead of silently claiming success. Quota-full migration keeps readable data in memory, blocks unsaved writes and asks for free space/reload. Recovery snapshots are never replaced; malformed prayer updates are isolated without dropping valid prayer text.

Private data: localStorage, unencrypted, this browser only. Guest uses the original keys; authenticated accounts use hfg-private:<account-id>: keys. Auth readiness gates private rendering, and account changes remount the state provider and feature drafts. Sign-in never adopts or uploads guest data. Scoped backup enumeration cannot include another profile. This is application isolation, not encryption or a device lock. See PRIVACY_DATA_FLOW.md. `JournalRepository` separates typed CRUD from UI; encrypted synchronization would require a new implementation, key recovery policy, RLS and explicit consent. Public sharing opens a separate composer and requires an explicit publish. Source attachments contain passage/devotional paths; private text is never placed in URLs. State holds preferences, theme, bookmarks, highlight colors, read chapters, saved devotionals, progress, walk steps and notification preferences. There are no actual scheduled notifications.

## Shared interface and the forward step (phase 01.1)

`src/ui` holds the presentational components every screen is built from (screen and toolbar, grouped lists and rows, sheets and confirmations, the segmented control, the tab bar, the Today cover, the shelf, the layer block, the Lamplight notice). They take props and know nothing of storage; the logic stays in `src/platform`, `src/features` and the feature modules. `src/platform/appearance.ts` and `AppearanceProvider.tsx` own the look and Lamplight. The additive forward step `upgradeV3Fields` in `src/platform/persistence.ts` gives a stored v2 or v3 profile the fields `lamplight`, `shelf` and `lastChapter`; the version stays 3, the step is idempotent, and a profile that already has all three is returned byte for byte. The shelf (the context checks read to the end) is account-scoped private state; the live look and Lamplight choice are not part of the profile.

## Scripture

`bible/provider.ts` supplies an asynchronous `BibleProvider` and local search capped at 60 matches. Official WEB JSON includes books, chapters and numbered verses; the importer removes USFM formatting, headings, the speaker labels of Song of Songs, footnotes, cross references and word attributes, preserving verse words. Edition-omitted verses have an explicit `omitted` marker and show an edition note instead of invented Scripture. In Song of Songs a verse may carry `speakers` (`{ at, label }`, `at` a character offset into the text, 0 before the first word): the WEB's speaker labels, kept apart from the verse text. The Reader and the site's chapter pages show them as small labels above or inside the verse, with one line explaining them (`speakerParts` and `speakerNote` in `bible/provider.ts`); search, sharing, quotes and notes use the text alone. JSON is fetched once and statically precached, not copied into React's JavaScript bundle.

Provenance: official updated WEB Protestant USFM, retrieved 2026-10-07, 66 books, 1,189 chapters, 31,103 numbered records, 5,269,139 bytes. SHA-256: `0814165126036bfb21bfec15b26b822c58e39a792840edb91a918abf7928df4c`. Reproduce with `node scripts/import-web.mjs EXTRACTED_OFFICIAL_ARCHIVE_DIRECTORY`. Regenerated on 2026-10-14 from the archive downloaded that day (`engwebp_usfm.zip`, SHA-256 `6b47e6553ce0bd71902fe4b4ba71a5d7d862928e2ce47936acdda345bc6c5dd0`, source files dated 2026-10-13), once per fix; each time the importer as it stood before the fix still produced the previous file byte for byte from it, so only the fix changed the text. First, `scripts/usfm.mjs` keeps the space after a closing marker such as `\wj*`; before it, 142 New Testament verses ran two words together ("only bornSon"). 148 spaces were added and nothing else changed. Second, it drops `\sp` lines, the speaker labels of Song of Songs (Beloved, Lover, Friends, Brothers); before, 29 of them ended up as words inside 27 verses ("…which is Solomon’s. Beloved"). Those 29 words were removed and nothing else changed. Third, the importer records where each of the 33 `\sp` labels starts (`speakers`): no verse text changed, and Song of Songs verses gained only that field. `tests/bible-text.test.ts` guards all three. Do not substitute a scraped or licensed source. Text licensing is public domain; observe the WEB name/trademark restrictions if changing translation words.

The reader shows the chapter text with one toolbar; a per-verse sheet and a chapter sheet hold the actions and the three layers (Context, AI explanation, Community) as separate pages, and the Study view is gone. Curated textual observations exist for Psalms 23/121 and Romans 8; other chapters show an honest unavailable-context state. Study supplies labeled editorial questions, not fabricated scholarship. No historical commentary, Greek/Hebrew dataset or denomination-specific commentary is supplied. Source headings/verses are linked. Community experiences do not establish passage meaning.

## Server authorization

Browser uses the public Supabase key and caller session. RLS guards original tables and owner-only terms, drafts, reports and block lists. New public feeds use explicitly constrained SECURITY DEFINER RPCs with empty search paths; raw new post tables are not readable by application roles. Public return types omit anonymous authors' auth UUIDs, private notes, reporter identity and reactor lists. Author snapshots come from the private profile, never the request. Server time, author, moderation, review state and counters are not client-writeable.

Terms are versioned and timestamped by the server, enforced for new contributions, original chat/prayer inserts and support submission. New posts serialize per author with a durable 30-second cooldown; legacy chat retains its original 3-second SQL guard. Reactions have uniqueness constraints. Migration 004 separates server-owned public prayer update history from the original 2,000-character body; constrained feeds combine them for display, without exposing raw write access. Each public update is at most 1,000 characters, with 50,000 characters of retained history. Aggregate feed uses a `(created_at,id)` cursor and 20 rows; original chat retains 50-row pagination and Realtime, original wall retains latest/most-prayed 50. New feed refreshes on actions and re-entry; it does not claim Realtime. Block management exposes opaque block-record IDs; raw block rows and the author-UUID predicate are not callable/readable by app roles. Blocks and mutes filter all public server readers, including anonymous authors resolved privately by content ID. Staff can identify authors for moderation.

## Giving boundary

The CharityCatalogProvider returns isolated curated records; ExternalFundraisingProvider validates hosted fundraiser destinations. External catalog links are verified exact destinations. Support requests are private drafts and under_review until an operator uses a privileged review function. Public RPC includes only approved/fundraising, visible, undeleted, unexpired rows. Content edits after approval are unavailable to authors: close and submit a new reviewed request rather than silently changing approved claims. Duplicate active URLs, malformed domains, direct payment instructions and client moderation bypass are rejected. Title/story/relationship/country disallow inline URLs and recognizable financial instructions; URLs belong in the allowlisted field. The same guard excludes older unsafe approved records from public RPCs and prevents approval, without destroying private source records. These validation rules cannot replace manual scam review. Displayed targets are declared/unverified; actual progress is viewed at the provider.

`giving/contracts.ts` defines recipient verification, checkout, contribution, webhook, payout, refund and dispute models. Stripe/Mollie adapters always reject and make no API requests. A future server must validate credentials, webhook signatures, recipient/KYC state, legal approval and explicit production flag together. It must derive amounts/currency on the server, deduplicate provider event IDs and idempotency keys, reconcile provider balances and payment states, handle out-of-order events, refunds/disputes and recipient restrictions. Client flags cannot enable this integration. No production native payment database or simulated success flow is included.

## Themes, capabilities, PWA and native

Five token blocks in `src/styles.css` (constants, Cover Light, Cover Lamplight, Marked Light, Marked Lamplight) cover surfaces, text, buttons, focus, borders, shadows and highlights; `site/scripts/sync-shared.mjs` copies the same blocks into the site and stops the build when they differ. The reader's look (`hfg-look`: Cover and story or Marked page) and Lamplight setting (`hfg-lamplight`: Automatic, On or Off) are two device-only localStorage keys that reach `<html>` as `data-look` and `data-mode`; a head script sets both before React, and `AppearanceProvider` and `platform/appearance.ts` run the same logic afterwards, following the device's dark setting under Automatic. The older `hfg-appearance` and `hfg-theme` keys are read once and removed. Theme-color follows the resolved value. Navigation observes safe areas and 44px targets. Static fonts are self-hosted; reduced motion from the original stylesheet remains. Native dialog handles focus/Escape for external checkout confirmation.

`Capabilities` centralizes enabled and unavailable services. Build-time public configuration permits community access, subject to schema and auth setup; it does not prove hosted readiness. WEB/external charity links are available independently. Licensed translations, production payments, native push, Google/Apple auth are disabled.

Native integration boundary: replace browser persistence, external URL/share, deep-link and notification adapters with platform implementations without changing feature domains. A future Capacitor wrapper must use an external system browser for giving, handle universal/app links and safe areas, test secure local storage and authentication return links, and support account-deletion requirements. Wrapper/deep-link device setup is not implemented or tested. PWA precache contains only static application/Bible assets; there is no dynamic response cache. Never place private records or auth responses in a shared cache.

Future notifications require owner-only subscription/token storage and preference enforcement, explicit OS permission only after configuration, timezone-aware scheduling, server-held APNs/FCM/Web Push credentials, logout/unsubscribe cleanup and deep-link validation. Push payloads must avoid private prayer/journal/support text. Delivery, token registration and scheduling are not implemented.

## Expansion modules

`topics/graph.ts` defines stable TopicId/label/alias relationships and the Resource contract. Existing devotional labels/order/IDs are preserved. Preferences and following stay local and do not imply server membership. `social/TopicHub.tsx` extends the existing community posts, reports and block systems; no parallel social content store. Migration 005 owns explicit private memberships, constrained topical readers and vote RPCs. Read MIGRATIONS.md for grants, deployment limits and the authorization matrix. Sources are plain text with validated HTTPS links; no preview fetch or scraping exists.

`features/Journeys.tsx` contains two optional editorial paths and one seven-practice private challenge, using actual existing Scripture/prayer/journal routes. Progress is a private user choice and persists after leaving. My Walk composes actual saved counts, focus, followed topics and progress without competitive scoring. Private prayer records may contain answeredAt and real returned public testimony IDs. No private prayer ID is transmitted to the publishing RPC.

`bible/knowledge.ts` supports verse→passage→chapter→book fallback and separates Scripture from sourced editorial observations. The current knowledge corpus is unchanged: three chapter observations, not universal historical/linguistic coverage. `assembleGrounding` accepts only selected public Scripture and available notes. GroundedStudyProvider is an unconfigured server interface; no model request is made. `future/contracts.ts` has entitlement/organization/contributor-provider contracts only; no client activation or approval method. Other broader social services are future design work, not implemented flows.


## Circles v1 (local implementation; undeployed)
The Community namespace adds /community/circles and /community/circles/:slug?thread=:uuid. src/social/Circles.tsx owns discovery, creation/details, membership/application actions, scoped moderation and group discussions. circleContracts.ts maps RPC result types and validates untrusted response shapes against actual SQL serializer tests; circlesApi.ts supplies bounded 12-second, abortable RPC requests; it contains no cache or offline queue. Auth/account boundaries remount drafts; offline/background/focus/block events clear server records and idle visible pages recheck every 30 seconds. Periodic revalidation skips in-flight loads/mutations, so a valid slow sequence can finish; each individual RPC remains bounded at 12 seconds. Permission changes apply immediately on the server; already read content cannot be remotely unread, and an open foreground view can remain stale until its next recheck.

006_circles.sql adds only circles and circle_memberships, with default-deny RLS and no application table grants; community_posts gains nullable circle_id. Existing post/reply/source/vote/reaction/report/block/Terms/cooldown/audit systems are reused. Group lists, discussions, members/applications and reports are capped at 20 and use stable cursors. Roles and counts come from the server; there is no member directory for ordinary clients. Moderator review records use opaque membership IDs, snapshots and an own-record flag, never auth UUIDs/emails. Moderator rights are specific to one active Circle and convey no platform role or verified expertise.

All legacy community/topic/Scripture/devotional/testimony/saved-thread readers exclude ALL Circle contributions. Circle votes still use the original tables/helpers, while ALL Circle contributions are excluded from global reputation to avoid membership/activity inference. Private Circle sources remain member-provided HTTPS links, not fetched previews or verified scholarship. There is no social search/profile recommendation/activity endpoint that reads Circle records. No private Circle table is added to Realtime or service-worker caches. See CIRCLES_QA.md for the read-path inventory and evidence.
